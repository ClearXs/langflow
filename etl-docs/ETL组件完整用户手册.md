## 文档简介

### 关于本手册

本手册详细介绍了 Langflow ETL 工具集中所有数据处理组件的使用方法、配置说明和最佳实践。ETL (Extract, Transform, Load) 是数据处理的核心流程,本工具集提供了丰富的组件来简化数据处理工作。

### 目标读者

- 数据工程师
- 数据分析师
- ETL 开发人员
- 系统集成工程师

### 使用建议

**新手用户**建议按以下顺序学习:
1. 数据清洗组件 - 了解基础的数据处理
2. CSV/Excel 输入输出组件 - 掌握数据导入导出
3. 字段名映射组件 - 学习字段重命名
4. 去重组件 - 学习数据去重操作

**进阶用户**可重点关注:
1. 双流关联组件 - 复杂的数据关联
2. 分组聚合组件 - 数据统计分析
3. 数据加密/脱敏组件 - 数据安全处理
4. 字段透视/逆透视组件 - 数据结构转换

## 数据处理组件

数据处理组件 (Manipulations) 用于对数据进行各种转换和处理操作,包括清洗、映射、转换、拆分、合并等。

---

### 数据清洗组件

**组件名称**: ETL Data Cleaning
**图标**: eraser (橡皮擦)
**功能**: 通过规则对数据进行清洗、转换和脱敏处理

#### 概述

数据清洗组件是 ETL 工具集的核心组件之一,用于对数据进行过滤、转换、格式化和脱敏处理。通过灵活的规则配置,您可以轻松清理和标准化数据,为后续的数据处理流程做好准备。

**核心功能**:
- **条件过滤**: 根据指定条件筛选需要处理的数据记录
- **数据转换**: 支持 30+ 种内置转换规则
- **数据脱敏**: 内置多种脱敏规则,保护敏感信息
- **自定义处理**: 支持 Expression、JavaScript、Python 脚本
- **批量处理**: 可同时为多个字段配置不同的清洗规则

**适用场景**:
- 数据导入前的标准化处理
- 敏感数据脱敏(符合数据安全和隐私保护要求)
- 数据格式转换(日期、数字、字符串等)
- 数据质量提升(去除空格、统一大小写等)
- 条件化数据清洗

#### 快速入门

假设您有一批用户数据,需要对手机号进行脱敏处理:

**步骤 1**: 准备数据源
添加一个 CSV Input 或 API Input 组件,连接到数据清洗组件的"数据输入"端口。

**步骤 2**: 配置清洗规则
在"清洗规则"表格中添加规则:

| 字段名称 | 转换规则 | 自定义表达式 |
|---------|---------|-------------|
| phone | 手机号脱敏(mask_phone) | (留空) |
| name | 去除两端空格(trim) | (留空) |

**步骤 3**: 运行测试
点击"运行组件",然后点击"查看输出"验证结果。

**步骤 4**: 连接下游组件
将清洗后的数据连接到其他 ETL 组件或输出组件。

> **提示**: 初次使用时,建议先不配置过滤条件,对所有数据应用清洗规则。

#### 参数说明

**输入参数**:

**1. 数据输入 (data_input)**
- 类型: Data (列表)
- 必填: 是
- 说明: 要清洗的输入数据,支持 CSV/Excel 文件、API 响应、数据库查询结果等

**2. 过滤条件 (filter_conditions)**
- 类型: Table
- 必填: 否
- 默认值: 空(处理所有记录)
- 说明: 通过配置过滤条件,只对符合条件的记录应用清洗规则

表格字段:
| 字段 | 说明 |
|-----|------|
| 字段名称 | 用于比较的字段名 |
| 运算符 | 比较运算符(=, !=, >, <, >=, <=, 包含, 正则等) |
| 比较值 | 用于比较的目标值 |
| 逻辑运算符 | 多条件组合逻辑(AND/OR) |

**支持的运算符**:

*比较运算符*:
- 等于(=), 不等于(!=)
- 大于(>), 小于(<)
- 大于等于(>=), 小于等于(<=)

*字符串运算符*:
- 包含, 不包含
- 开头是, 结尾是

*列表运算符*:
- 在列表中, 不在列表中

*正则表达式*:
- 正则匹配

**3. 清洗规则 (cleaning_rules)**
- 类型: Table
- 必填: 是
- 说明: 为不同字段配置清洗转换规则

表格字段:
| 字段 | 说明 | 必填 |
|-----|------|-----|
| 字段名称 | 要应用清洗规则的字段名 | 是 |
| 转换规则 | 从预定义规则中选择 | 是 |
| 自定义表达式 | 某些规则需要的额外参数 | 视规则而定 |

**转换规则分类**:

**(1) 类型转换**
| 规则 | 说明 | 示例 |
|-----|------|------|
| to_number | 转换为数字 | "123" → 123 |
| to_int | 转换为整数 | "123.45" → 123 |
| to_float | 转换为浮点数 | "123" → 123.0 |
| to_str | 转换为字符串 | 123 → "123" |
| to_bool | 转换为布尔值 | "true" → True |

**(2) 字符串处理**
| 规则 | 说明 | 示例 |
|-----|------|------|
| trim | 去除两端空格 | " hello " → "hello" |
| trim_all | 去除所有空格 | " h e l l o " → "hello" |
| upper | 转大写 | "hello" → "HELLO" |
| lower | 转小写 | "HELLO" → "hello" |
| replace_string | 替换字符串 | 表达式: old&#124;new |
| substring_after | 获取之后部分 | 表达式: delimiter |
| substring_before | 获取之前部分 | 表达式: delimiter |
| substring | 按位置截取 | 表达式: start,length |

**(3) 数据脱敏**
| 规则 | 说明 | 示例 |
|-----|------|------|
| mask_phone | 手机号脱敏 | 13812345678 → 138\*\*\*\*5678 |
| mask_idcard | 身份证脱敏 | 110101199001011234 → 110101\*\*\*\*\*\*\*\*1234 |
| mask_email | 邮箱脱敏 | user@example.com → u\*\*\*@example.com |
| mask_name | 姓名脱敏 | 张三 → 张\*, 欧阳锋 → 欧\*\* |

**(4) 日期时间**
| 规则 | 说明 | 示例 |
|-----|------|------|
| timestamp_to_string | 时间戳转字符串 | 格式: YYYY-MM-DD HH:mm:ss |
| date_format | 日期格式化 | 格式: 源格式&#124;目标格式 |

**(5) 编码加密**
| 规则 | 说明 |
|-----|------|
| md5 | MD5哈希 |
| sha256 | SHA256哈希 |

**(6) 特殊处理**
| 规则 | 说明 | 示例 |
|-----|------|------|
| amount_to_chinese | 金额转中文大写 | 12345.67 → 壹万贰仟叁佰肆拾伍元陆角柒分 |
| none | 保持原值不变 | - |

**(7) 自定义脚本**
| 规则 | 说明 | 表达式格式 |
|-----|------|-----------|
| expression | 简单表达式 | value * 2 + 10 |
| javascript | JavaScript代码 | return value.toUpperCase() |
| python | Python代码 | return str(value).upper() |

> **信息**: 在自定义脚本中,`value` 代表当前字段的值,`record` 代表整条记录

**4. 最大转换记录 (max_records)**
- 类型: Integer
- 必填: 否
- 默认值: 0 (不限制)
- 说明: 限制处理的最大记录数,用于测试或性能控制

**输出参数**:

**清洗后数据 (cleaned_data)**
- 类型: Data (列表)
- 说明: 经过过滤和清洗后的数据,保持原有结构但字段值已转换

输出特点:
- 保留所有字段(包括未配置规则的字段)
- 只包含符合过滤条件的记录
- 字段值已按清洗规则转换

#### 使用示例

**示例 1: 用户信息脱敏**

场景: 对用户数据进行脱敏处理,保护隐私信息

配置:

过滤条件:
```
字段名称: status
运算符: 等于(=)
比较值: active
```

清洗规则:
| 字段名称 | 转换规则 | 自定义表达式 |
|---------|---------|-------------|
| phone | 手机号脱敏 | - |
| id_card | 身份证脱敏 | - |
| email | 邮箱脱敏 | - |
| name | 姓名脱敏 | - |

输入数据:
```json
[{
  "name": "张三",
  "phone": "13812345678",
  "email": "zhangsan@example.com",
  "id_card": "110101199001011234",
  "status": "active"
}]
```

输出数据:
```json
[{
  "name": "张*",
  "phone": "138****5678",
  "email": "z***@example.com",
  "id_card": "110101********1234",
  "status": "active"
}]
```

**示例 2: 数据标准化**

场景: 统一数据格式,清理脏数据

清洗规则:
| 字段名称 | 转换规则 | 自定义表达式 |
|---------|---------|-------------|
| name | 去除两端空格 | - |
| email | 转小写 | - |
| age | 转为整数 | - |
| join_date | 日期格式化 | YYYY/MM/DD&#124;YYYY-MM-DD |

输入数据:
```json
[{
  "name": "  张三  ",
  "email": "ZhangSan@Example.COM",
  "age": "25",
  "join_date": "2024/01/15"
}]
```

输出数据:
```json
[{
  "name": "张三",

```

#### 高级功能

**字段分析功能**

点击"分析字段"按钮,组件会自动分析输入数据的字段结构,包括:
- 所有可用字段名称
- 字段数据类型推断
- 字段示例值

**嵌套字段访问**

支持使用点号(.)访问嵌套对象:

```json
{
  "user": {
    "profile": {
      "name": "张三",
      "contact": {
        "phone": "13812345678"
      }
    }
  }
}
```

访问方式:
- 字段名称: `user.profile.name`
- 字段名称: `user.profile.contact.phone`

**自定义表达式详解**

Expression 表达式:
```javascript
value * 1.1              // 价格上浮10%
value > 100 ? "高" : "低"  // 条件表达式
```

JavaScript 脚本:
```javascript
// 字符串处理
return value.toUpperCase().trim();

// 访问记录
if (record.age > 18) {
    return "成年";
}
```

Python 脚本:
```python
# 字符串处理
return str(value).upper().strip()

# 访问记录
if record.get('age', 0) > 18:
    return "成年"
```

> **注意**:
> - 脚本执行有性能开销,大数据量时谨慎使用
> - 确保脚本总是返回一个值
> - 脚本错误会导致该记录处理失败

#### 性能优化

**处理大数据集**:
1. 使用最大记录限制测试规则
2. 优化过滤条件,尽早过滤数据
3. 避免复杂脚本,优先使用内置规则

**规则配置优化**:
1. 合理排序: 先简单规则,再复杂规则
2. 避免冗余: 不需要转换的字段不配置规则
3. 批量测试: 使用 max_records=100 快速验证

#### 常见问题

**问题 1: 过滤条件不生效**

症状: 配置了过滤条件,但所有数据都被处理

可能原因:
- 字段名称拼写错误(区分大小写)
- 比较值类型不匹配
- 逻辑运算符配置错误

解决方法:
1. 使用"分析字段"功能检查字段名
2. 检查实际字段类型
3. 简化条件逐步测试

**问题 2: 脱敏规则无效**

症状: 脱敏后仍显示完整信息

可能原因:
- 字段值格式不符合预期
- 字段为空值

解决方法:
1. 先使用 trim 规则清理字段
2. 检查原始数据格式
3. 考虑使用自定义脚本

#### 安全与合规

**数据脱敏最佳实践**:

1. 识别敏感数据: 手机号、身份证、邮箱、姓名
2. 脱敏等级选择:
   - 数据环境: 全量脱敏
   - 运行环境日志: 必须脱敏
   - 数据分析: 根据需要选择脱敏规则
3. 不可逆加密: 密码使用 SHA256

**合规性建议**:
- GDPR (欧盟通用数据保护条例)
- PIPL (中华人民共和国个人信息保护法)
- 等保 2.0 (网络安全等级保护)

> **警告**:
> - 脱敏是单向操作,无法恢复原始数据
> - 不要在运行环境直接修改原始数据
> - 确保脱敏后的数据仍可用于业务分析

### 字段名映射组件

**组件名称**: ETL Field Name Mapping
**图标**: shuffle (洗牌)
**功能**: 将源字段名映射到目标字段名,用于数据转换

#### 概述

字段名映射组件用于重命名数据中的字段,将源字段名映射为目标字段名。这是 ETL 流程中常见的操作,用于:
- 统一不同数据源的字段命名
- 符合目标系统的字段命名规范
- 提高数据可读性和理解性
- 实现字段级别的数据转换

**核心功能**:
- **批量重命名**: 一次配置多个字段的映射关系
- **字段类型检测**: 自动识别源字段的数据类型
- **灵活配置**: 可选择保留或删除未映射的字段
- **自动解析**: 自动从上游组件提取字段信息
- **映射验证**: 检测重复的目标字段名

**适用场景**:
- 数据源与目标系统字段名不一致
- 统一多个数据源的字段命名
- 字段名国际化(中文转英文或反向)
- 符合企业数据标准和规范
- 提高数据可理解性

#### 快速入门

假设您从外部系统导入数据,需要将字段名转换为企业标准命名:

**步骤 1**: 准备数据源
连接包含需要重命名字段的数据源。

**步骤 2**: 配置字段映射
在"字段映射"表格中添加映射规则:

| 源字段 | 源字段类型 | 目标字段 | 备注 |
|-------|-----------|---------|------|
| userName | str | user_name | 用户名 |
| userAge | int | age | 年龄 |
| emailAddr | str | email | 邮箱地址 |

**步骤 3**: 运行组件
点击"运行组件"查看映射结果。

> **提示**: 使用"自动解析字段"按钮可以快速加载上游数据的字段列表

#### 参数说明

**输入参数**:

**1. 数据输入 (data_input)**
- 类型: Data (列表)
- 必填: 是
- 说明: 包含需要重命名字段的输入数据

**2. 字段映射 (field_mappings)**
- 类型: Table
- 必填: 是
- 说明: 定义源字段到目标字段的名称映射

表格字段:
| 字段 | 说明 | 编辑 |
|-----|------|-----|
| 源字段 | 输入数据中的原始字段名 | 可编辑 |
| 源字段类型 | 源字段的数据类型(自动检测) | 只读 |
| 目标字段 | 输出数据中的新字段名 | 可编辑 |
| 备注 | 关于此映射规则的可选说明 | 可编辑 |

**3. 删除未映射字段 (drop_unmapped)**
- 类型: Boolean
- 必填: 否
- 默认值: False
- 说明:
  - True: 只保留映射表中指定的字段
  - False: 保留所有字段,未映射的字段保持原名称

**输出参数**:

**映射后数据 (data)**
- 类型: Data (列表)
- 说明: 字段名已按映射规则重命名的数据

#### 使用示例

**示例 1: 统一字段命名**

场景: 将驼峰命名转换为下划线命名

输入数据:
```json
[{
  "userName": "张三",
  "userAge": 25,
  "emailAddr": "zhangsan@example.com",
  "phoneNumber": "13812345678"
}]
```

映射配置:

**功能**: 转换数据流中字段的数据类型

#### 概述

- 批量字段转换配置

**适用场景**:
- 数据类型标准化
- CSV/Excel数据类型修正(默认都是字符串)
- 数值计算前的类型准备
- 布尔值标准化处理
- 日期格式统一

#### 高级功能

**1. 自动类型检测**

点击"加载字段"按钮时,组件会:
1. 从上游组件获取样本数据
2. 分析每个字段的数据类型
3. 自动填充type_conversions表格
4. 显示检测到的源类型

**2. 严格模式与宽松模式**

**strict_validation = true (严格模式,默认)**:
- 转换失败时抛出错误并停止
- 适用于要求数据完整性的场景
- 可及时发现数据质量问题

**strict_validation = false (宽松模式)**:
- 转换失败时保留原值并继续
- 在日志中记录警告
- 适用于允许部分数据不规范的场景

示例:
```json
输入: {"age": "invalid"}
严格模式: 抛出错误 "Cannot convert 'invalid' to integer"
宽松模式: 保留原值 {"age": "invalid"} 并记录警告
```

**3. 类型转换规则**

**String → Integer/Float**:
- 去除空格
- 支持负数: "-123" → -123
- Float可转Integer: "3.14" → 3 (向下取整)

**String → Boolean**:
- 不区分大小写
- 支持多种表示: "TRUE", "True", "true" 都识别为true
- 可自定义规则

**String → Datetime**:
- 支持多种日期格式
- 自动解析(不指定规则时)
- 输出统一为ISO8601格式

**Integer/Float → String**:
- 直接转为字符串表示
- 保留数值格式: 123 → "123", 3.14 → "3.14"

**Float → Integer**:
- 向下取整: 3.9 → 3
- 警告: 可能丢失小数精度

#### 常见问题与解决方案

**问题1: 类型转换失败**

**症状**: "ValueError: Cannot convert 'abc' to integer"

**可能原因**:
1. 源数据包含非法字符
2. 日期格式不匹配
3. 布尔值格式不标准

**解决方法**:
1. 检查源数据质量
2. 使用数据清洗组件预处理
3. 指定正确的conversion_rule
4. 使用宽松模式(strict_validation=false)

**问题2: 日期解析错误**

**症状**: "Cannot parse datetime"

**解决方法**:
1. 检查conversion_rule格式字符串
2. 确保源数据格式与规则一致
3. 使用标准日期格式(yyyy-MM-dd)
4. 对于复杂格式,使用自定义脚本

**问题3: 布尔值转换不正确**

**症状**: 预期为true但得到false

**解决方法**:
1. 检查布尔值的实际内容(可能有空格)
2. 使用自定义conversion_rule
3. 在数据清洗组件中先标准化布尔值

示例:

**问题4: 自动检测类型不准确**

**症状**: 数字被检测为字符串

**原因**: 样本数据中可能混有非数字值

**解决方法**:
1. 手动修改target_type
2. 使用数据清洗组件过滤异常值
3. 在宽松模式下允许部分转换失败

**问题5: 转换后精度丢失**

**症状**: Float转Integer后小数部分丢失

**说明**: 这是预期行为,Float → Integer会向下取整

**解决方法**:
- 如需保留小数,使用Float类型
- 如需四舍五入,先用计算组件处理

### 字段值映射组件

**组件名称**: Field Value Mapping
**图标**: map (地图/映射)
**功能**: 基于条件比较映射字段值,支持多字段和各种比较运算符

#### 概述

字段值映射组件用于根据字段值的条件判断来转换数据。它类似于编程语言中的 if-then-else 逻辑,可以根据字段值匹配不同的条件,输出相应的替换值。这对于数据标准化、编码转换、分类处理等场景非常有用。

**核心功能**:
- **多种比较运算符**: 支持等于、不等于、大于、小于、包含、正则表达式等 13 种运算符
- **多字段映射**: 可同时配置多个字段的映射规则
- **灵活输出**: 支持创建新字段或覆盖原字段
- **脚本扩展**: 支持 JavaScript 和 Python 自定义脚本实现复杂逻辑
- **自动字段分析**: 自动加载上游字段并预填充样本值

**适用场景**:
- **编码转换**: 将代码转换为可读文本(例如: 1→男性, 2→女性)
- **数据分类**: 根据数值范围分类(例如: 年龄→年龄段)
- **数据标准化**: 统一不同来源的字段值格式
- **条件计算**: 根据条件赋予不同的值
- **数据清洗**: 将异常值替换为标准值

#### 快速入门

**基础配置示例**:

输入数据:
```json
[{
  "gender_code": "1",
  "age": 28,
  "status": "active"
}]
```

映射规则配置:
| 输入字段 | 运算符 | 比较值 | 替换值 | 输出字段 |
|---------|-------|--------|--------|---------|
| gender_code | = | 1 | 男性 | gender_text |
| gender_code | = | 2 | 女性 | gender_text |
| status | = | active | 正常 | status_text |
| age | >= | 60 | 老年 | age_group |

输出数据:
```json
[{
  "gender_code": "1",
  "age": 28,
  "status": "active",
  "gender_text": "男性",
  "status_text": "正常",
  "age_group": "老年"
}]
```

> **提示**: 对于同一个输出字段,第一个匹配的规则会生效,后续规则不再处理(首次匹配原则)

#### 参数说明

**基础参数**:

| 参数名称 | 类型 | 必填 | 默认值 | 说明 |
|---------|------|------|--------|------|
| data_input | Data[] | 是 | - | 要转换的输入数据流 |
| mapping_rules | Table | 是 | [] | 映射规则配置表 |

**映射规则表结构**:

| 列名 | 类型 | 说明 |
|-----|------|------|
| input_field | string | 要读取值进行比较的字段名称 |
| field_type | string | 输入字段的数据类型(自动检测,只读) |
| operator | dropdown | 比较运算符 |
| compare_value | string | 与输入字段值进行比较的值 |
| replacement_value | string | 条件匹配时输出的值 |
| output_field | string | 写入替换值的字段名称 |

**支持的运算符**:

| 运算符 | 名称 | 说明 | 示例 |
|-------|------|------|------|
| = | 等于 | 完全相等 | field = "A" |
| != | 不等于 | 不相等 | field != "B" |
| > | 大于 | 数值/字符串比较 | age > 18 |
| < | 小于 | 数值/字符串比较 | price < 100 |
| >= | 大于等于 | 数值/字符串比较 | score >= 60 |
| <= | 小于等于 | 数值/字符串比较 | discount <= 0.5 |
| contains | 包含 | 字符串包含子串 | name contains "张" |
| not_contains | 不包含 | 字符串不包含子串 | email not_contains "@" |

#### 高级功能

**1. 自动字段分析**

点击"分析字段"按钮,组件会:
- 自动从上游组件获取数据样本
- 提取所有字段名和数据类型
- 预填充比较值为样本数据的第一个值
- 自动设置输出字段名与输入字段名相同

这大大简化了规则配置,特别是处理大量字段时。

**2. 首次匹配原则**

当同一个输出字段有多条规则时,组件采用"首次匹配原则":
- 从上到下逐条检查规则
- 一旦某条规则匹配,就应用该规则并跳过后续规则
- 未匹配任何规则时,不创建或修改该输出字段

**示例**:
```
规则1: age >= 60 → age_group = "老年"
规则2: age >= 35 → age_group = "中年"
规则3: age >= 18 → age_group = "青年"

age=70 时,只会匹配规则1,输出"老年",不会再检查规则2和规则3
```

**3. 脚本模式**

脚本模式允许编写自定义逻辑:

**JavaScript 示例**:
```javascript

    row.priority = 1;

// 字符串处理
row.full_name = row.first_name + ' ' + row.last_name;

// 数学计算
row.total = row.price * row.quantity;
```

**Python 示例**:
```python

    result['category'] = 'Premium'
```

#### 性能优化

**1. 规则顺序优化**

将最常匹配的规则放在前面,减少不必要的比较:

**【错误】** **低效顺序**:
```
规则1: status = "archived" (1%)
规则2: status = "deleted" (2%)
规则3: status = "active" (90%)
规则4: status = "inactive" (7%)
```

**【正确】** **优化顺序**:
```
规则1: status = "active" (90%)
规则2: status = "inactive" (7%)
规则3: status = "deleted" (2%)
规则4: status = "archived" (1%)
```

**2. 避免重复正则表达式计算**

对于相同的正则表达式,只定义一次:

**【错误】** **低效配置**:
```
field1 regex "^1[3-9]\d{9}$"
field2 regex "^1[3-9]\d{9}$"
field3 regex "^1[3-9]\d{9}$"
```

**【正确】** **优化配置**:
```
先用脚本创建统一的验证字段,再基于该字段进行映射
```

**3. 脚本性能优化**

在脚本中避免复杂计算:
- 不要在循环中进行重复计算
- 缓存计算结果
- 避免使用递归
- 尽量使用规则表代替脚本

**4. 大数据量处理**

处理大数据量时:
- 优先使用简单运算符(=、!=)而非复杂运算符(regex)
- 减少映射规则数量
- 考虑拆分为多个组件分步处理

#### 常见问题与解决方案

**问题 1: 规则配置后不生效**

**症状**: 配置了映射规则,但输出数据没有新字段

**可能原因**:
1. 比较值类型不匹配(例如: 字符串 "1" vs 数值 1)
2. 运算符选择错误
3. 输入字段名拼写错误

**解决方案**:
1. 检查字段类型,必要时转换为字符串比较
2. 使用"分析字段"功能查看实际数据类型
3. 手动输入字段名前,先用"分析字段"加载字段列表

**问题 2: 多个规则冲突**

**症状**: 同一个输出字段被配置了多条规则,不知道哪条会生效

**解决方案**:
- 理解"首次匹配"原则
- 将最具体的规则放在前面
- 使用不同的输出字段名避免冲突

**示例**:
```
**【正确】** 正确:
规则1: age < 18 → minor = "是"
规则2: age >= 18 → minor = "否"

**【错误】** 可能有问题:
规则1: age >= 18 → category = "成年"
规则2: age >= 60 → category = "老年"
(70岁会匹配第1条,输出"成年"而非"老年")

**【正确】** 修正:
规则1: age >= 60 → category = "老年"
规则2: age >= 18 → category = "成年"
```

**问题 3: 正则表达式不匹配**

**症状**: 确信数据符合模式,但正则表达式不匹配

**可能原因**:
1. 特殊字符未转义
2. 正则语法错误
3. 数据中有不可见字符(空格、换行等)

**解决方案**:
1. 使用在线正则表达式测试工具验证
2. 检查是否需要转义: `. * + ? ^ $ { } [ ] \ | ( )`
3. 先用 trim() 清理数据空格

**常用正则模式**:
```
手机号: ^1[3-9]\d{9}$
邮箱: ^[a-zA-Z0-9_-]+@[a-zA-Z0-9_-]+(\.[a-zA-Z0-9_-]+)+$
身份证: ^\d{17}[0-9Xx]$
日期(YYYY-MM-DD): ^\d{4}-\d{2}-\d{2}$
```

**问题 4: 脚本执行错误**

**症状**: 启用脚本后组件报错

**可能原因**:
1. 语法错误
2. 访问不存在的字段
3. 类型错误

**解决方案**:
1. 先在浏览器控制台或 Python 环境测试脚本
2. 使用安全的字段访问: `row.get('field', default_value)`
3. 添加类型检查和错误处理

**JavaScript 安全访问**:
```javascript
// 不安全
row.user.profile.name

// 安全
row.user?.profile?.name || 'Unknown'
```

**Python 安全访问**:
```python
# 不安全
result['name'] = row['user']['profile']['name']

# 安全
result['name'] = row.get('user', {}).get('profile', {}).get('name', 'Unknown')
```

**问题 5: 性能问题**

**症状**: 处理大量数据时组件很慢

**解决方案**:
1. 减少正则表达式规则数量
2. 优化规则顺序(高频规则放前面)
3. 简化脚本逻辑
4. 考虑在数据库层面完成部分映射

#### 最佳实践

**1. 规则设计原则**

- **明确性**: 每条规则应该清晰明确,避免歧义

**5. 规则表 vs 脚本选择**

### 单列拆分多行组件

**组件名称**: Field Split
**图标**: split (拆分)
**功能**: 将单列数据按分隔符拆分为多行数据

#### 概述

单列拆分多行组件用于将包含多个值的字段(使用特定分隔符连接)拆分成多条记录。这在处理合并数据、标签列表、多值字段等场景中非常有用。

**核心功能**:
- **多种分隔符**: 支持逗号、分号、制表符、管道符、空格、换行符和自定义分隔符
- **正则表达式**: 支持使用正则表达式作为分隔规则
- **空值处理**: 可选择保留或删除拆分后的空值
- **序号重置**: 可为拆分后的行重新分配序号
- **分块处理**: 支持大数据量分块处理,避免内存溢出

**适用场景**:
- **标签展开**: 将"标签1,标签2,标签3"拆分为多条记录
- **多值字段处理**: 拆分产品分类、用户权限等多值字段
- **数据扁平化**: 将聚合数据恢复为明细数据
- **文本分行**: 按换行符将长文本拆分为多行

> **信息**: 此组件与"单列拆分多列"组件不同。本组件是垂直拆分(增加行数),而拆分多列是水平拆分(增加列数)

#### 快速入门

**基础配置示例**:

输入数据:
```json
[{
  "product_id": "P001",
  "tags": "电子产品,数码,热销"
}]
```

配置:
- split_field: tags
- separator: , (逗号)
- reset_index: false
- keep_empty: false

输出数据:
```json
[
  {"product_id": "P001", "tags": "电子产品"},
  {"product_id": "P001", "tags": "数码"},
  {"product_id": "P001", "tags": "热销"}
]
```

> **提示**: 原始记录的其他字段(product_id)会被复制到每条拆分后的记录中

#### 常见问题与解决方案

**问题 1: 拆分后行数不符合预期**

**症状**: 预期拆分5行,实际只有3行

**可能原因**:
1. keep_empty = False 导致空值被删除
2. 分隔符选择错误
3. 数据中分隔符不一致

**解决方案**:
1. 临时设置 keep_empty = True 查看完整结果
2. 使用"预览"功能检查分隔符
3. 查看统计信息中的拆分数量

**问题 2: 包含分隔符的数据被意外拆分**

**症状**: "公司名称: A,B,C有限公司"被拆成3行

**解决方案**:
1. 源数据中对特殊字符进行转义
2. 使用不同的分隔符
3. 数据清洗时替换掉内容中的分隔符

**问题 3: 正则表达式不生效**

**症状**: 设置了正则表达式但结果不对

**可能原因**:
1. separator_type 未设置为"正则表达式"
2. 正则语法错误
3. 特殊字符未转义

**解决方案**:
1. 确认 separator_type 配置正确
2. 使用在线工具测试正则表达式
3. 转义特殊字符: `. * + ? ^ $ { } [ ] \ | ( )`

**问题 4: 内存溢出**

**症状**: 处理大数据集时报内存错误

**解决方案**:
1. 减小 chunk_size 值
2. 分批处理数据
3. 增加系统内存

**问题 5: 中文分隔符问题**

**症状**: 使用中文逗号(,)拆分失败

**解决方案**:
1. 统一使用英文分隔符
2. 使用自定义分隔符,输入中文逗号
3. 数据预处理时替换中文标点为英文标点

### 字段值合并组件

**组件名称**: Field Value Merge
**图标**: git-merge (合并)
**功能**: 合并多个字段值,支持字符串连接和数学运算

#### 概述

字段值合并组件用于将两个或多个字段的值进行合并,生成新的字段。支持字符串连接(LINK)和数学运算(加减乘除、取余),是数据整合和计算的重要工具。

**核心功能**:
- **字符串连接**: 使用自定义分隔符连接字段值
- **数学运算**: 支持加、减、乘、除、取余运算
- **类型转换**: 自动或手动指定结果数据类型
- **多字段处理**: 一次配置可合并多组字段
- **删除源字段**: 可选择在合并后删除源字段

**适用场景**:
- **生成全名**: 合并姓和名
- **拼接地址**: 组合省市区地址
- **金额计算**: 计算总价、折扣等
- **生成编码**: 组合多个字段生成唯一标识
- **数值统计**: 对多个数值字段求和、求积

#### 性能优化

**1. 合理规划合并顺序**

将不依赖其他合并结果的规则放在前面:

**【错误】** **低效顺序**:
```
1. final = total * discount (依赖 total)
2. total = price * quantity
```

**【正确】** **优化顺序**:
```
1. total = price * quantity
2. final = total * discount
```

**2. 避免不必要的类型转换**

保持字段类型一致,减少转换开销:

**【错误】** **频繁转换**:
```
"100"(string) * "2"(string) → 需要两次转换
```

**【正确】** **类型一致**:
```
100(number) * 2(number) → 无需转换
```

**3. 合理使用 drop_source_fields**

删除不需要的字段可以:
- 减少数据量
- 节省内存
- 提高后续处理速度

但要确保删除的字段不会在后续流程中使用。

**4. 大数据量处理**

对于百万级数据:
- 尽量减少合并规则数量
- 避免复杂的链式合并
- 考虑分批处理

#### 常见问题与解决方案

**问题 1: 数学运算结果为 NaN**

**症状**: 运算结果显示 NaN 或空值

**可能原因**:
1. 字段值包含非数字字符
2. 字段值为空
3. 除数为 0

**解决方案**:
1. 使用数据清洗组件预处理数据
2. 确保数值字段格式正确
3. 添加数据验证逻辑

**问题 2: 分隔符不显示**

**症状**: 字符串连接时分隔符没有出现

**可能原因**:
1. 分隔符列为空
2. 运算类型选择错误

**解决方案**:
1. 确认分隔符列已填写(如果需要分隔符)
2. 确认运算类型为 "A LINK B"

**问题 3: 精度丢失**

**症状**: 浮点数计算结果不精确

**示例**:
```
0.1 + 0.2 = 0.30000000000000004
```

**解决方案**:
1. 设置合适的 decimal_precision
2. 使用整数计算后再转换(金额计算建议使用分为单位)

**问题 4: 字段列表未加载**

**症状**: 点击"加载字段列表"后没有反应

**可能原因**:
1. 未连接上游组件
2. 上游组件无数据输出
3. 网络或系统错误

**解决方案**:
1. 检查组件连接
2. 确认上游组件能正常输出数据
3. 查看日志信息

**问题 5: 源字段被意外删除**

**症状**: 启用 drop_source_fields 后,需要的字段也被删除了

**解决方案**:
1. 关闭 drop_source_fields 选项
2. 在后续组件中手动删除不需要的字段
3. 仔细检查哪些字段参与了合并

#### 最佳实践

**1. 命名规范**

新字段命名建议:
- 使用有意义的名称: `full_name` 而非 `field1`
- 保持命名风格一致: `total_price`, `final_amount`
- 区分计算字段: 加 `_calc` 或 `_computed` 后缀

**2. 合并策略**

| 场景 | 建议运算 | 值类型 |
|------|---------|--------|
| 姓名合并 | A LINK B | string |
| 地址拼接 | A LINK B (使用分隔符) | string |
| 金额计算 | A * B / A + B | float |
| 数量统计 | A + B | integer |
| 编码生成 | A LINK B (使用下划线) | string |

**3. 数据验证**

合并前检查:
- 字段是否存在
- 数据类型是否匹配
- 是否有空值

合并后验证:
- 结果是否符合预期
- 是否有异常值(NaN, Infinity)
- 数据格式是否正确

**4. 错误处理**

建议的数据准备流程:
1. 数据清洗(去除空值、异常值)
2. 类型转换(统一数据类型)
3. 字段合并
4. 结果验证

**5. 性能考虑**

对于大数据量:
- 限制合并规则数量(建议 ≤ 5条)
- 避免过长的链式合并(建议 ≤ 3层)
- 及时删除不需要的字段
- 监控内存使用

**6. 文档化**

建议记录:
- 每个合并规则的业务含义
- 分隔符的选择原因
- 数据类型转换规则
- 计算公式说明

**7. 测试建议**

- 使用小数据集测试
- 测试边界情况(0, 负数, 特殊字符)
- 验证类型转换
- 检查精度设置

### 单列拆分多列组件

**组件名称**: Field Split To Columns
**图标**: columns (列)
**功能**: 将单列数据按分隔符拆分为多个新列

#### 概述

单列拆分多列组件用于将包含多个值的字段(使用分隔符连接)横向拆分成多个独立的列。与"单列拆分多行"不同,本组件是水平拆分(增加列数),适用于固定格式的数据展开。

**核心功能**:
- **多种分隔符**: 支持逗号、分号、制表符、管道符、空格、换行符和自定义分隔符
- **正则表达式**: 支持使用正则表达式作为分隔规则
- **自定义列名**: 可配置新列的名称和顺序
- **最大拆分数**: 可限制拆分列数
- **默认值填充**: 对不足的列填充默认值
- **分块处理**: 支持大数据量分块处理

**适用场景**:
- **地址拆分**: 将"省-市-区"拆分为3列
- **日期拆分**: 将"2024-01-15"拆分为年、月、日
- **坐标拆分**: 将"经度,纬度"拆分为2列
- **固定格式数据展开**: CSV格式的字段展开

> **信息**: 本组件与"单列拆分多行"相反。本组件是水平拆分(增加列数),拆分多行是垂直拆分(增加行数)

#### 快速入门

**基础配置示例**:

输入数据:
```json
[{
  "order_id": "001",
  "location": "北京-朝阳区-建国门"
}]
```

配置:
- source_field: location
- delimiter: - (管道符)
- new_fields_config:
  - {field_name: "province", field_order: 0}
  - {field_name: "district", field_order: 1}
  - {field_name: "street", field_order: 2}
- drop_source_field: True

输出数据:
```json
[{
  "order_id": "001",
  "province": "北京",
  "district": "朝阳区",
  "street": "建国门"
}]
```

> **提示**: 拆分后的新列会添加到原数据中,可选择删除源字段

### 字段透视组件

**组件名称**: Field Pivot
**图标**: table-properties (表格属性)
**功能**: 将行数据转换为列(pivot操作)

#### 概述

字段透视组件用于将行格式的数据转换为列格式,类似于Excel的数据透视表。它将某个字段的唯一值转换为列名,并填充对应的值,实现数据的重新组织和聚合。

**核心功能**:
- **行转列**: 将纵向数据转换为横向数据
- **分组聚合**: 支持按字段分组
- **8种聚合函数**: first, last, sum, mean, max, min, count, concat
- **字段映射**: 可自定义转换后的列名
- **空值填充**: 支持自定义填充值

**适用场景**:
- **宽表生成**: 将长格式数据转换为宽格式
- **数据透视**: 生成数据透视表
- **报表生成**: 按维度展开数据
- **交叉分析**: 多维数据分析

#### 快速入门

**基础配置示例**:

输入数据:
```json
[
  {"student": "张三", "subject": "数学", "score": 90},

  {"student": "李四", "subject": "数学", "score": 88},
  {"student": "李四", "subject": "英语", "score": 92}
]
```

配置:
- group_fields: student
- key_field: subject
- value_field: score
- agg_function: first

输出数据:
```json
[
  {"student": "张三", "数学": 90, "英语": 85},
  {"student": "李四", "数学": 88, "英语": 92}
]
```

> **提示**: pivot操作将"科目"字段的值(数学、英语)转换为了新的列名

### 多行合并为一行组件

**组件名称**: Field Rows Merge
**图标**: merge (合并)
**功能**: 将多行数据合并为一行

多行合并为一行组件用于将多条记录合并成单条记录。支持多种合并策略,可以保留特定行、聚合数值或拼接文本。通常与分组功能配合使用。

**核心功能**:
- **8种合并策略**: keep_first, keep_last, merge_all, sum, mean, max, min, concat
- **分组合并**: 支持按字段分组
- **灵活分隔符**: 多种文本连接分隔符
- **字段类型识别**: 自动识别数值和文本字段
- **排除字段**: 可指定不参与合并的字段

**适用场景**:

- **分组汇总**: 按组聚合数据

- **统计计算**: 求和、平均等

#### 快速入门

## 数据操作组件

数据操作组件 (Operations) 用于对数据流进行关联、聚合、去重和合并等复杂操作。这些组件通常涉及多个数据流之间的交互,是构建复杂 ETL 流程的关键。

---

### 双流关联组件

**组件名称**: Dual Stream Join
**图标**: git-merge (分支合并)
**功能**: 使用内连接/左连接/右连接/全连接合并两个数据流,支持多条件和多种操作符

#### 概述

双流关联组件用于将两个独立的数据流基于指定条件进行关联合并。类似于 SQL 中的 JOIN 操作,支持等值连接和非等值连接,可以实现复杂的数据关联逻辑。

**核心功能**:
- **多种连接类型**: 支持 inner(内连接)、left(左连接)、right(右连接)、outer(全连接)
- **多条件关联**: 支持配置多个关联条件,条件之间为 AND 关系
- **多种操作符**: 支持 =、!=、>、<、>=、<= 六种比较操作符
- **字段预览**: 自动预览合并后的字段列表
- **智能前缀**: 自动为重复字段添加前缀,避免字段名冲突
- **类型对齐**: 自动对齐连接键的数据类型,提高兼容性

**适用场景**:
- 用户表和订单表关联
- 主表和维度表关联
- 事件流和配置流关联
- 多源数据整合
- 基于时间范围的数据关联

#### 快速入门

假设您有两个数据流:订单表和客户表,需要根据客户 ID 进行关联:

**步骤 1**: 准备数据源
添加两个数据输入组件:
- 左侧数据流(订单表): order_id, customer_id, amount, order_date
- 右侧数据流(客户表): customer_id, name, email, level

**步骤 2**: 连接数据流
将两个数据源分别连接到双流关联组件的"左侧数据流"和"右侧数据流"输入端口。

**步骤 3**: 加载字段列表
在"连接条件"表格中,点击"加载字段列表"按钮,组件会自动从上游获取可用字段。

**步骤 4**: 配置连接条件
在"连接条件"表格中添加关联条件:

| 左表字段 | 操作符 | 右表字段 |
|---------|-------|---------|
| customer_id | = | customer_id |

**步骤 5**: 选择连接类型
选择适合的连接类型:
- **inner**: 只保留两表都匹配的记录
- **left**: 保留左表所有记录,右表不匹配时为空
- **right**: 保留右表所有记录,左表不匹配时为空
- **outer**: 保留两表所有记录

**步骤 6**: 预览输出字段
点击"预览输出字段"按钮,查看合并后的字段结构。

**步骤 7**: 运行测试
点击"运行组件",验证关联结果。

> **提示**: 使用左连接(left)可以保留订单表的所有记录,即使某些客户信息缺失。

#### 参数说明

**输入参数**:

**1. 左侧数据流 (left_stream)**
- **类型**: Data[] (列表)
- **必填**: 是
- **说明**: 第一个表输入组件的数据流,通常作为主表

**2. 右侧数据流 (right_stream)**
- **类型**: Data[] (列表)
- **必填**: 是
- **说明**: 第二个表输入组件的数据流,通常作为关联表

**3. 连接类型 (join_type)**
- **类型**: Dropdown (下拉选择)
- **必填**: 是
- **默认值**: inner
- **选项**:
  - **inner**: 内连接,只保留两表都匹配的记录
  - **left**: 左连接,保留左表所有记录
  - **right**: 右连接,保留右表所有记录
  - **outer**: 全连接,保留两表所有记录
- **说明**: 选择 JOIN 连接方式

**4. 连接条件 (join_conditions)**
- **类型**: Table (表格)
- **必填**: 是
- **表格列**:
  - **left_key**: 左表字段名
  - **operator**: 操作符(=, !=, >, <, >=, <=)
  - **right_key**: 右表字段名
- **说明**: 配置两个数据流的连接条件,支持多条件

**5. 输出字段 (output_fields)** [高级]
- **类型**: Table (表格,只读)
- **说明**: 查看 JOIN 后的输出字段列表,显示字段名、来源和数据类型

**6. 左表前缀 (left_prefix)** [高级]
- **类型**: String
- **必填**: 否
- **默认值**: left_
- **说明**: 左表字段冲突时的前缀

**7. 右表前缀 (right_prefix)** [高级]
- **类型**: String
- **必填**: 否
- **默认值**: right_
- **说明**: 右表字段冲突时的前缀

**8. 删除重复 (drop_duplicates)** [高级]
- **类型**: Boolean
- **必填**: 否
- **默认值**: False
- **说明**: 连接后删除重复行

**输出参数**:

**1. 连接后数据 (data)**
- **类型**: Data[]
- **说明**: 合并后的数据流,包含两个表的字段

**2. 连接统计 (join_stats)**
- **类型**: Data
- **说明**: 连接操作的统计信息(左表记录数、右表记录数、结果记录数等)

**3. 字段预览 (field_preview)**
- **类型**: Data
- **说明**: 字段信息预览(字段名、来源、冲突处理方式)

#### 使用示例

**示例 1: 基础内连接**

场景: 订单表和客户表关联,只保留有客户信息的订单

配置:
- 左侧数据流: 订单表(order_id, customer_id, amount)
- 右侧数据流: 客户表(customer_id, name, email)
- 连接类型: inner
- 连接条件:
  ```
  customer_id = customer_id
  ```

结果: 只返回客户表中存在的订单记录

**示例 2: 多条件关联**

场景: 根据客户 ID 和订单日期区间进行关联

配置:
- 连接条件:
  | 左表字段 | 操作符 | 右表字段 |
  |---------|-------|---------|
  | customer_id | = | customer_id |
  | order_date | >= | valid_from |
  | order_date | <= | valid_to |

说明: 第一个条件使用等值连接,后两个条件作为过滤条件

**示例 3: 左连接保留主表数据**

场景: 订单表关联客户表,保留所有订单(即使客户信息缺失)

配置:
- 连接类型: left
- 连接条件:
  ```
  customer_id = customer_id
  ```
- 删除重复: False

结果: 保留订单表的所有记录,客户信息缺失时对应字段为空

#### 高级功能

**1. 字段冲突处理**

当两个表有同名字段时,组件会自动添加前缀:

示例:
- 左表字段: customer_id, name, amount
- 右表字段: customer_id, name, level

合并后字段:
- customer_id (连接键,只保留一份)
- name_left_ (左表的 name)
- name_right_ (右表的 name)
- amount (左表独有)
- level (右表独有)

**2. 类型自动对齐**

组件会自动对齐连接键的数据类型:
- 数值类型优先(int、float)
- 无法转换为数值时统一为字符串
- 避免因类型不匹配导致的关联失败

**3. 动态字段加载**

点击"加载字段列表"按钮时,组件会:
1. 尝试执行上游节点获取实际数据
2. 如果执行失败,从上游节点配置中提取字段
3. 自动填充连接条件的示例配置

**4. 输出字段预览**

点击"预览输出字段"按钮查看:
- 所有输出字段的名称
- 字段来源(左表/右表)
- 推断的数据类型

#### 性能优化

**1. 连接顺序优化**

将数据量小的表放在右侧:
```
左表(大表): 1,000,000 行
右表(小表): 1,000 行
```

**2. 连接键索引**

确保连接键字段:
- 数据类型一致
- 无空值或使用默认值填充
- 已建立索引(针对数据库源)

**3. 过滤条件优先**

在连接前使用数据清洗组件过滤不需要的记录:
```
数据清洗(过滤条件) → 双流关联
```

**4. 内存管理**

处理大数据集时:
- 使用 inner 而非 outer,减少结果集
- 启用"删除重复"选项
- 限制输出字段数量

#### 常见问题与解决方案

**问题 1: 连接结果为空**

**症状**: 配置了连接条件,但结果集为空

**可能原因**:
1. 连接键字段值不匹配
2. 数据类型不兼容
3. 字段名拼写错误

**解决方法**:
1. 使用预览功能检查两个数据流的实际数据
2. 检查连接键是否有空值
3. 使用数据清洗组件统一数据格式
4. 尝试使用左连接或右连接诊断问题

**问题 2: 字段名冲突**

**症状**: 合并后字段名有 `_left_` 或 `_right_` 后缀

**原因**: 两个表有同名字段

**解决方法**:
1. 在双流关联前使用字段名映射组件重命名字段
2. 自定义前缀(修改 `left_prefix` 和 `right_prefix`)
3. 使用输出字段预览功能提前查看结果

**问题 3: 关联结果记录数异常**

**症状**: 结果记录数远大于预期(数据膨胀)

**原因**:
1. 连接键不唯一,产生笛卡尔积
2. 多条件中使用了不等值条件

**解决方法**:
1. 使用去重组件预处理数据
2. 添加更多等值连接条件
3. 启用"删除重复"选项
4. 检查连接键的唯一性

#### 最佳实践

**1. 连接类型选择**

根据业务需求选择合适的连接类型:
- **数据补全**: 使用 left 或 right,保留主表数据
- **精确匹配**: 使用 inner,只保留匹配记录
- **数据合并**: 使用 outer,保留所有数据

**2. 连接条件设计**

- 优先使用等值条件(=)
- 非等值条件放在等值条件之后
- 避免使用过多的非等值条件(影响性能)

**3. 字段命名规范**

- 连接前统一字段命名
- 避免使用系统保留字
- 使用字段名映射组件重命名冲突字段

**4. 数据质量保证**

- 关联前进行数据清洗
- 处理空值和默认值
- 统一数据类型和格式
- 使用字段值映射规范枚举值

### 分组聚合组件

**组件名称**: Group By
**图标**: layers (图层)
**功能**: 按指定列分组并应用聚合函数

#### 概述

分组聚合组件用于对数据进行分组统计和聚合计算,类似于 SQL 中的 GROUP BY 操作。支持多种聚合函数,可以快速进行数据统计分析。

**核心功能**:
- **多字段分组**: 支持按多个字段进行分组
- **10种聚合函数**: sum、count、count_distinct、avg、min、max、median、std、first、last
- **自定义别名**: 为聚合结果自定义输出列名
- **自动字段分析**: 从上游数据自动提取可用字段
- **空值处理**: 可选择是否排除包含空值的分组
- **结果排序**: 可按分组字段对结果排序
- **无聚合分组**: 支持只分组不聚合(类似 SQL DISTINCT)

**适用场景**:
- 销售数据统计(按地区/产品分组汇总)
- 用户行为分析(按用户分组统计活跃度)
- 日志数据聚合(按时间段统计错误数)
- 数据去重(按关键字段分组取唯一值)
- 报表数据汇总

#### 快速入门

假设您有销售订单数据,需要按产品分类统计销售额和订单数:

**步骤 1**: 准备数据源
添加 CSV Input 或其他数据源组件,数据包含:
- category (产品分类)
- product_name (产品名称)
- amount (金额)
- quantity (数量)

**步骤 2**: 连接数据流
将数据源连接到分组聚合组件的"数据输入"端口。

**步骤 3**: 分析字段
在"分组字段"表格中,点击"分析字段"按钮,组件会自动加载所有可用字段。

**步骤 4**: 选择分组字段
从自动填充的字段列表中,删除不需要的字段,保留:
- category (产品分类)

**步骤 5**: 配置聚合函数
在"聚合配置"表格中,点击"分析字段"按钮加载字段,然后配置:

| 字段名 | 聚合函数 | 别名 |
|-------|---------|------|
| amount | 求和 | total_amount |
| amount | 平均值 | avg_amount |
| product_name | 计数 | order_count |

**步骤 6**: 运行测试
点击"运行组件",查看分组统计结果。

> **提示**: 可以对同一个字段应用多种聚合函数,例如同时计算销售额的总和和平均值。

#### 参数说明

**输入参数**:

**1. 数据输入 (data_input)**
- **类型**: Data[] (列表)
- **必填**: 是
- **说明**: 要分组的输入数据

**2. 分组字段 (group_by_columns)**
- **类型**: Table (表格)
- **必填**: 是
- **表格列**:
  - **field_name**: 字段名称
- **说明**: 选择用于分组的列。点击"分析字段"可从上游数据自动填充

**3. 聚合配置 (aggregations)**
- **类型**: Table (表格)
- **必填**: 否(可以只分组不聚合)
- **表格列**:
  - **field_name**: 要聚合的字段名
  - **agg_function**: 聚合函数
    - 求和 (sum)
    - 计数 (count)
    - 去重计数 (count_distinct)
    - 平均值 (avg)
    - 最小值 (min)
    - 最大值 (max)
    - 中位数 (median)
    - 标准差 (std)
    - 首个值 (first)
    - 末个值 (last)
  - **alias**: 别名(可选,聚合结果的输出列名)
- **说明**: 为每个字段定义聚合函数

**4. 删除空值 (drop_na)** [高级]
- **类型**: Boolean
- **必填**: 否
- **默认值**: True
- **说明**: 排除分组列中包含空值的行

**5. 排序结果 (sort_results)** [高级]
- **类型**: Boolean
- **必填**: 否
- **默认值**: False
- **说明**: 按分组列排序结果

**输出参数**:

**1. 分组数据 (data)**
- **类型**: Data[]
- **说明**: 分组聚合后的数据

**2. 预览数据 (preview_data)**
- **类型**: Data[]
- **说明**: 前 100 行分组数据

**3. 分组统计 (group_stats)**
- **类型**: Data
- **说明**: 分组操作的统计信息(分组字段、聚合配置、分组数量、输入记录数)

#### 常见问题与解决方案

**问题 1: 分组后记录数为 0**

**症状**: 配置了分组字段和聚合,但结果为空

**可能原因**:
1. 输入数据为空
2. 所有记录的分组字段都是空值(且 drop_na=True)
3. 字段名拼写错误

**解决方法**:
1. 使用预览数据输出检查输入
2. 检查字段名是否在"分析字段"后正确加载
3. 将 drop_na 设置为 False 查看是否有空值数据
4. 查看组件状态消息获取错误详情

**问题 2: 聚合结果不符合预期**

**症状**: 统计结果明显错误

**可能原因**:
1. 字段数据类型不匹配(如文本字段使用 sum)
2. 数据包含空值或异常值
3. 选择了错误的聚合函数

**解决方法**:
1. 使用字段类型转换组件预处理数据
2. 使用数据清洗组件处理空值
3. 使用 count 函数先验证分组是否正确

**问题 3: 未配置聚合但期望统计**

**症状**: 只返回了分组字段,没有聚合统计

**原因**: 聚合配置表格为空,组件执行类似 DISTINCT 的操作

**解决方法**:
1. 在"聚合配置"表格中添加至少一个聚合
2. 点击"分析字段"按钮加载可用字段
3. 为每个需要统计的字段配置聚合函数

选择合适的分组维度:
- 避免使用唯一值字段(如 ID)作为分组键
- 优先使用离散度较低的字段(如类别、地区)
- 多维度分组时从粗到细排列

使用清晰的别名:

```
avg_price
customer_count

# 避免
sum
avg
cnt
```

**4. 结果排序**

启用结果排序:
- 便于阅读和分析
- 便于下游组件处理
- 特别适合按时间分组的场景

保留金额最大记录:
```
排序字段: amount
排序方向: 降序 (desc)
```

保留优先级最高记录:
```
排序字段: priority
排序方向: 升序 (asc)
```

**2. 合并字段策略**

合并模式下:
- **比较字段**: 保留第一条记录的值
- **非比较字段**: 合并所有唯一值

示例:
```
# 比较字段: customer_id
# 非比较字段: tags

输入:
customer_id | tags
------------|------
1001        | VIP
1001        | 活跃
1001        | VIP

输出:
customer_id | tags
------------|----------
1001        | VIP,活跃
```

**3. 自动字段加载**

点击"从上游加载字段"按钮时,组件会:
1. 尝试执行上游节点获取实际数据
2. 如果失败,从上游节点配置中提取字段
3. 自动填充所有字段到比较字段表格
4. 同时更新排序字段下拉选项

#### 性能优化

**1. 减少比较字段数量**

```
# 快: 使用唯一性高的字段
比较字段: phone

# 慢: 使用过多字段
比较字段: name, gender, age, city, ...
```

**2. 选择合适的去重模式**

```
# 快速: 删除模式
去重模式: delete

# 较慢: 合并模式(需要遍历和连接)
去重模式: merge
```

**3. 排序字段索引**

如果使用排序字段:
- 确保排序字段数据完整
- 数值型字段比字符串型快
- 避免对大文本字段排序

**4. 预过滤数据**

在去重前过滤不需要的记录:
```
数据清洗(过滤) → 去重组件
```

#### 常见问题与解决方案

**问题 1: 去重后记录数没有变化**

**症状**: 原始记录数和去重后记录数相同

**可能原因**:
1. 实际没有重复数据
2. 比较字段选择不当
3. 字段值包含隐藏字符(空格、换行等)

**解决方法**:
1. 使用分组聚合组件验证是否有重复
2. 检查比较字段是否正确
3. 在去重前使用数据清洗组件清理字段值
4. 查看去重统计信息确认情况

**问题 2: 保留了错误的记录**

**症状**: 期望保留最新记录,实际保留了旧记录

**可能原因**:
1. 排序方向设置错误
2. 排序字段数据类型不正确
3. 排序字段包含空值

**解决方法**:
1. 检查排序方向:保留最新应使用降序 (desc)
2. 使用字段类型转换组件规范排序字段类型
3. 使用数据清洗组件处理空值

**问题 3: 合并模式输出格式异常**

**症状**: 合并后的字段值格式混乱

**可能原因**:
1. 原始数据包含分隔符字符
2. 字段值包含特殊字符

**解决方法**:
1. 使用不常见的分隔符(如 " | " 或 ";;")
2. 在去重前使用字段值映射组件替换特殊字符
3. 考虑使用删除模式代替合并模式

#### 最佳实践

**1. 比较字段选择**

选择合适的比较字段:
- 优先使用唯一标识字段(ID、手机号、邮箱)
- 多字段组合时从最唯一的开始
- 避免使用低区分度字段(性别、地区等)

**2. 去重模式选择**

根据业务需求选择:
- **删除模式**: 适用于完全重复的记录
- **合并模式**: 适用于需要保留所有信息的场景

**3. 排序策略**

合理使用排序:
```
# 保留最新
registration_date DESC

# 保留最旧
registration_date ASC

# 保留优先级高
priority ASC

# 保留金额大
amount DESC
```

**4. 数据预处理**

去重前进行数据清洗:
1. 去除字段两端空格
2. 统一大小写
3. 处理空值
4. 规范化日期格式

### 多流合并组件

**组件名称**: Multi Stream Union
**图标**: layers (图层)
**功能**: 合并多个数据流(最多 5 个)

#### 概述

多流合并组件用于将多个独立的数据流纵向合并为一个数据流。类似于 SQL 中的 UNION ALL 操作,支持模式对齐和字段筛选,适用于整合来自不同数据源的数据。

**核心功能**:
- **多流输入**: 支持最多 5 个数据流同时合并
- **模式对齐**: 自动对齐各数据流的列模式,缺失字段填充空值
- **字段筛选**: 可选择保留或排除特定字段
- **来源标识**: 可选择是否添加数据来源标识列
- **自动去重**: 支持合并后删除重复行
- **字段预览**: 自动分析所有数据流的字段

**适用场景**:
- 多个数据源的数据整合
- 历史数据和增量数据合并
- 不同格式数据的统一
- 多分片数据的汇总
- A/B 测试数据合并

#### 快速入门

假设您有三个数据源(华北、华东、华南销售数据),需要合并为全国销售数据:

**步骤 1**: 准备数据源
添加三个数据输入组件:
- 华北销售数据: region, product, amount, date
- 华东销售数据: region, product, amount, date
- 华南销售数据: region, product, amount, date

**步骤 2**: 连接数据流
将三个数据源分别连接到多流合并组件的:
- 数据流1 (必填)
- 数据流2
- 数据流3

**步骤 3**: 加载字段列表
在"字段配置"表格中,点击"加载字段列表"按钮,组件会自动分析所有数据流的字段。

**步骤 4**: 配置保留字段(可选)
在字段配置表格中,取消勾选不需要的字段:

| 字段名 | 来源数据流 | 保留字段 |
|-------|-----------|---------|
| region | stream_1, stream_2, stream_3 | ✓ |
| product | stream_1, stream_2, stream_3 | ✓ |
| amount | stream_1, stream_2, stream_3 | ✓ |
| date | stream_1, stream_2, stream_3 | ✓ |

**步骤 5**: 配置高级选项(可选)
- 对齐模式: 开启(默认)
- 删除重复: 根据需要选择
- 包含来源信息: 如需追踪数据来源则开启

**步骤 6**: 运行测试
点击"运行组件",验证合并结果。

> **提示**: 启用"包含来源信息"可以在合并后的数据中追踪每条记录来自哪个数据流。

#### 参数说明

**输入参数**:

**1. 数据流1-5 (stream_1 ~ stream_5)**
- **类型**: Data[] (列表)
- **必填**: stream_1 必填,其他可选
- **说明**:
  - stream_1: 第一个数据流(必填)
  - stream_2: 第二个数据流(可选)
  - stream_3-5: 高级选项,第三至第五个数据流(可选)

**2. 字段配置 (union_field_config)**
- **类型**: Table (表格,只读)
- **表格列**:
  - **field_name**: 字段名(只读)
  - **source_stream**: 来源数据流(只读)
  - **keep_field**: 保留字段(可编辑,勾选框)
- **说明**: 配置合并后需要保留的字段

**3. 删除重复 (drop_duplicates)** [高级]
- **类型**: Boolean
- **必填**: 否
- **默认值**: False
- **说明**: 合并后删除重复的行

**4. 对齐模式 (align_schemas)** [高级]
- **类型**: Boolean
- **必填**: 否
- **默认值**: True
- **说明**: 对齐各数据流的列模式,缺失字段填充空值

**5. 来源列名 (source_column)** [高级]
- **类型**: String
- **必填**: 否
- **默认值**: _source_stream
- **说明**: 数据流来源标识的列名

**6. 包含来源信息 (include_source_info)** [高级]
- **类型**: Boolean
- **必填**: 否
- **默认值**: False
- **说明**: 是否添加来源数据流标识列

**输出参数**:

**1. 合并后数据 (data)**
- **类型**: Data[]
- **说明**: 合并后的完整数据流

**2. 合并统计 (union_stats)**
- **类型**: Data
- **说明**: 合并操作的统计信息(数据流数量、各流记录数、合并后记录数)

**3. 字段预览 (field_preview)**
- **类型**: Data
- **说明**: 字段信息预览(字段名、来源、出现次数)

#### 高级功能

**1. 智能模式对齐**

`align_schemas = True` (默认):
- 自动补齐缺失字段
- 填充空值
- 保证输出结构统一

`align_schemas = False`:
- 仅保留所有数据流共有的字段
- 其他字段被丢弃
- 适用于严格模式匹配

**2. 字段来源分析**

加载字段列表后会显示:
```
field_name | source_stream
-----------|------------------
product    | stream_1, stream_2, stream_3
amount     | stream_1, stream_2
category   | stream_1
```

可据此判断:
- 哪些字段是公共字段
- 哪些字段只存在于部分数据流

**3. 合并后去重**

启用 `drop_duplicates = True`:
- 基于所有字段判断重复
- 适用于多个数据源可能有重复记录的场景
- 注意性能影响

**4. 来源追踪**

启用 `include_source_info = True`:
- 自动添加来源列
- 列名由 `source_column` 参数指定
- 值为 stream_1, stream_2 等

应用场景:
- 数据溯源
- 问题排查
- 数据质量分析

#### 性能优化

**1. 减少数据流数量**

```
# 优先合并
2-3 个数据流

# 避免
5 个满数据流同时合并
```

**2. 字段筛选**

只保留必要字段:
```
# 好: 只保留 5 个核心字段
product, amount, date, region, category

# 差: 保留所有字段(20+)
```

**3. 预处理数据**

在合并前:
1. 使用数据清洗组件过滤无效记录
2. 使用字段名映射组件统一字段名
3. 使用字段类型转换组件统一数据类型

**4. 去重策略**

```
# 方案1: 合并时去重(慢)
drop_duplicates = True

# 方案2: 合并后去重(快)
多流合并 → 去重组件
```

#### 常见问题与解决方案

**问题 1: 合并后字段数量异常**

**症状**: 期望 5 个字段,实际输出 10 个字段

**可能原因**:
1. 不同数据流的字段名不一致
2. 字段名有隐藏字符(空格等)
3. 字段配置中保留了所有字段

**解决方法**:
1. 使用字段预览输出检查实际字段
2. 在合并前使用字段名映射组件统一字段名
3. 在字段配置中取消勾选不需要的字段
4. 检查字段名是否完全一致(包括大小写)

**问题 2: 合并后记录数不符合预期**

**症状**: 期望记录数 = 所有流记录数之和,实际更少

**可能原因**:
1. 启用了 drop_duplicates
2. 某些数据流为空或未连接
3. align_schemas = False 导致数据丢失

**解决方法**:
1. 检查 drop_duplicates 设置
2. 使用合并统计输出查看各流的记录数
3. 将 align_schemas 设置为 True
4. 检查所有数据流是否正确连接

**问题 3: 字段值出现异常空值**

**症状**: 某些字段在部分记录中为空

**原因**: 不同数据流的字段不完全一致,align_schemas 填充了空值

**解决方法**:
1. 这是正常行为,符合 SQL UNION ALL 语义
2. 如不希望出现空值,在合并前使用数据清洗组件添加默认值
3. 或在合并后使用数据清洗组件填充空值

#### 最佳实践

**1. 数据流准备**

合并前确保:
- 字段名称统一(使用字段名映射组件)
- 字段类型一致(使用字段类型转换组件)
- 数据格式规范(使用数据清洗组件)

**2. 合并策略选择**

根据数据特点选择:
```
# 字段完全一致
align_schemas = False (更快)

# 字段部分不同
align_schemas = True (保证不丢数据)
```

**3. 去重时机**

合理选择去重时机:
```
# 数据量小
drop_duplicates = True

# 数据量大
多流合并 → 去重组件(更灵活)
```

**4. 来源追踪**

建议启用来源追踪:
- 便于问题排查
- 便于数据质量分析
- 对性能影响很小

### Flink 作业组件

**组件名称**: Flink Job
**图标**: Zap (闪电)
**功能**: 通过上传 JAR 文件或编写 Python 脚本提交 Flink 作业

#### 概述

Flink 作业组件用于向 Apache Flink 集群提交分布式计算作业。Apache Flink 是一个流处理和批处理统一的分布式计算引擎,支持:
- 实时流式数据处理
- 批量数据处理
- 复杂事件处理(CEP)
- 状态管理和容错

**核心功能**:
- **双模式支持**: 支持 JAR 文件和 Python 脚本两种作业提交方式
- **集群管理**: 连接和管理多个 Flink 集群
- **并行度配置**: 灵活设置作业执行的并行度
- **实时监控**: 查看作业提交状态和执行结果
- **代码编辑器**: 内置 Python 代码编辑器,支持语法高亮

**适用场景**:
- 实时数据流处理(日志分析、监控告警等)
- 批量数据处理(ETL、数据清洗等)
- 复杂事件处理(欺诈检测、风险控制等)
- 机器学习模型训练和推理
- 数据分析和统计

#### 快速入门

**场景**: 提交一个简单的 Python Word Count 作业

**步骤 1**: 选择 Flink 数据源
从下拉列表中选择已配置的 Flink 集群,或点击"添加数据源"创建新连接。

**步骤 2**: 选择作业模式
- **JAR 模式**: 上传编译好的 JAR 文件
- **Python 模式**: 直接编写 PyFlink 代码(默认)

**步骤 3**: 编写或粘贴代码
使用内置的示例代码或编写自己的 PyFlink 脚本:

```python
from pyflink.dataset import ExecutionEnvironment
from pyflink.table import TableConfig, BatchTableEnvironment

# 创建批处理环境
exec_env = ExecutionEnvironment.get_execution_environment()
t_config = TableConfig()
t_env = BatchTableEnvironment.create(exec_env, t_config)

# 执行作业逻辑...
```

**步骤 4**: 配置并行度(可选)
在高级选项中设置作业的并行度,默认为 1。

**步骤 5**: 提交作业
点击"运行组件"提交作业到 Flink 集群。

> **提示**: Python 模式适合快速原型开发和测试,JAR 模式适合运行环境部署

#### 参数说明

**输入参数**:

**1. Flink 数据源 (flink_datasource)**
- 类型: Dropdown
- 必填: 是
- 说明: 选择 Flink 集群数据源
- 功能:
  - 下拉选择已配置的 Flink 集群
  - 点击"添加数据源"按钮创建新连接
  - 支持实时刷新数据源列表

**2. 作业模式 (job_mode)**
- 类型: Dropdown
- 必填: 是
- 默认值: python
- 选项:
  - **jar**: JAR 文件模式
  - **python**: Python 脚本模式
- 说明: 选择作业提交方式

**JAR 模式参数**:

**3. JAR 文件 (jar_file)**
- 类型: File
- 必填: 是(JAR 模式下)
- 支持格式: .jar
- 说明: 选择要提交的 Flink JAR 文件

**4. 主类名称 (entry_class)**
- 类型: String
- 必填: 否
- 说明: 主类全限定名,例如: `com.example.MyFlinkJob`
- 注意: 如果 JAR 的 MANIFEST.MF 中已指定主类,可以留空

**5. 程序参数 (program_args)**
- 类型: String

```python
    )
"""

    create table mySink (
        word VARCHAR,
        `count` BIGINT
    ) with (
        'connector.type' = 'filesystem',
```

### Flink SQL 组件

**组件名称**: Flink SQL
**图标**: Database (数据库)
**功能**: 通过编写 Flink SQL 语句进行数据处理

#### 概述

Flink SQL 组件提供了使用标准 SQL 语法进行流式和批处理数据处理的能力。Flink SQL 是 Apache Flink 提供的高级 API,支持:
- 标准 SQL 语法(符合 ANSI SQL 标准)
- 流式SQL和批处理SQL统一语法
- 丰富的内置函数和连接器
- 动态表(Dynamic Table)概念
- 时间窗口和事件时间处理

**核心功能**:
- **SQL 编辑器**: 内置 SQL 代码编辑器,支持语法高亮
- **多语句支持**: 支持一次执行多条 SQL 语句
- **执行模式**: 支持批处理和流式两种执行模式
- **结果展示**: 实时显示每条语句的执行结果
- **语句分析**: 自动识别 SQL 语句类型(DDL/DML/Query)
- **Checkpoint 配置**: 流式模式下的检查点间隔设置

**适用场景**:
- 使用 SQL 进行 ETL 数据处理
- 实时数据仓库构建
- 流式数据分析和统计
- 数据集成和同步
- 复杂的多表关联查询

**示例 3: 多表关联**

场景: 关联用户表和订单表,生成用户订单汇总

SQL 脚本:
```sql

CREATE TABLE users (
    user_id BIGINT,
    user_name STRING,
    user_level STRING
) WITH (
    'connector' = 'jdbc',
    'url' = 'jdbc:mysql://localhost:3306/crm',
    'table-name' = 'users'
);

-- 订单事实表(批处理)
CREATE TABLE orders (
    order_id STRING,
    user_id BIGINT,
    amount DECIMAL(10, 2),
    order_date DATE
) WITH (
    'connector' = 'jdbc',
    'url' = 'jdbc:mysql://localhost:3306/crm',
    'table-name' = 'orders'
);

-- 结果表
CREATE TABLE user_order_summary (
    user_id BIGINT,
    user_name STRING,
    user_level STRING,
    order_count BIGINT,
    total_amount DECIMAL(10, 2)
) WITH (
    'connector' = 'jdbc',
    'url' = 'jdbc:mysql://localhost:3306/analytics',
    'table-name' = 'user_order_summary'
);

-- 关联查询并插入
INSERT INTO user_order_summary
SELECT
    u.user_id,
    u.user_name,
    u.user_level,
    COUNT(o.order_id) as order_count,
    COALESCE(SUM(o.amount), 0) as total_amount
FROM users u
LEFT JOIN orders o ON u.user_id = o.user_id
GROUP BY u.user_id, u.user_name, u.user_level;
```

- 执行模式: batch
- 并行度: 6

## 安全组件

安全组件 (Security) 用于对敏感数据进行加密和脱敏处理,确保数据在存储、传输和使用过程中的安全性,满足合规要求。

### 数据加密组件

**组件名称**: Data Encryption
**图标**: lock (锁)
**功能**: 使用外部规则加密字段数据

#### 概述

数据加密组件通过调用外部数据安全服务对指定字段进行加密处理。支持批量加密、多规则配置和自动字段加载,确保敏感数据在存储前得到充分保护。

**核心功能**:
- **批量加密**: 支持对多个字段同时加密
- **规则管理**: 与数据安全服务集成,使用统一的加密规则
- **自动字段加载**: 从上游数据自动提取字段列表
- **智能回退**: 当上游执行失败时,自动从配置中提取字段
- **加密统计**: 提供详细的加密操作统计信息
- **批处理优化**: 使用批量API提高加密性能

**适用场景**:
- 个人身份信息(PII)加密
- 银行卡号、身份证号加密
- 密码、密钥加密
- 满足GDPR、等保等合规要求
- 数据出境前的加密处理

```
id_card/idcard → 身份证脱敏规则
name/username → 姓名脱敏规则
```

**4. 批量处理优化**

与加密组件类似,采用批量API:
```python
# 批量脱敏请求
batch_requests = [
    {"ruleId": 201, "input": "13812345678", "requestId": "req_1"},
    {"ruleId": 201, "input": "13987654321", "requestId": "req_2"}
]

# 一次性处理
responses = await client.test_rule_batch_multi(batch_requests)
```

#### 性能优化

**1. 规则选择优化**

选择合适的脱敏规则:
```
# 快速脱敏规则
遮盖、截断 (本地计算)

# 较慢脱敏规则
哈希、加密 (需要加密库)
```

**2. 字段筛选**

只脱敏必要的字段:
```
# 需要脱敏
phone, email, id_card, bank_card

# 无需脱敏
user_id, create_time, status
```

**3. 分批处理**

大数据集分批脱敏:
```
每批处理: 1000-5000 条记录
总数据量: 100万条
预计耗时: 5-10分钟
```

**4. 缓存优化**

对于重复值,使用缓存:
```python
# 缓存脱敏结果
cache = {}
if value in cache:
    return cache[value]
else:
    masked = mask_value(value)
    cache[value] = masked
    return masked
```

#### 常见问题与解决方案

**问题 1: 脱敏后数据格式异常**

**症状**: 脱敏后的数据格式不符合预期

**可能原因**:
1. 规则配置与数据格式不匹配
2. 输入数据包含特殊字符
3. 脱敏规则有bug

**解决方法**:
1. 在数据安全服务中测试规则
2. 使用数据清洗组件预处理数据
3. 检查规则配置是否正确
4. 联系管理员修复规则

**问题 2: 脱敏后数据不一致**

**症状**: 相同输入产生不同输出

**可能原因**:
1. 使用了随机替换规则
2. 规则包含时间戳
3. 规则配置错误

**解决方法**:
1. 使用确定性脱敏规则(如哈希)
2. 检查规则是否包含随机因子
3. 在数据安全服务中验证规则行为

**问题 3: 脱敏率不符合预期**

**症状**: 部分数据未被脱敏

**可能原因**:
1. 字段包含空值
2. 数据格式不符合规则要求
3. 规则条件不满足

**解决方法**:
1. 检查空值处理策略
2. 使用数据清洗组件规范化格式
3. 查看脱敏统计信息获取详情

#### 最佳实践

**1. 脱敏规则设计**

- 批量写入优化

**1. Schema自动检测**

点击"自动检测Schema"按钮,组件会:
1. 消费少量样本消息
2. 分析JSON结构
3. 自动生成Schema配置

**2. 流式与批量模式对比**

| 特性 | 批量模式 | 流式模式 |
|------|---------|---------|
| continuous_poll | false | true |
| 输出方式 | 一次性返回所有消息 | 持续输出消息流 |
| 适用场景 | 定时任务、离线分析 | 实时监控、实时处理 |
| 消费者生命周期 | 任务完成后关闭 | 持续运行 |

**3. 消费者组管理**

- `force_new_group=true`: 每次创建新的消费者组,从头消费
- `force_new_group=false`: 使用固定消费者组,继续上次位置
- `reset_offsets=true`: 强制重置偏移量到earliest

##### 常见问题与解决方案

**问题1:连接Kafka失败**

**解决方法**:
1. 检查datasource_selector配置
2. 验证Kafka集群地址和端口
3. 检查SASL认证配置
4. 使用connection_test输出测试连接

**问题2:收不到消息**

**解决方法**:
1. 检查topics名称是否正确
2. 尝试auto_offset_reset="earliest"
3. 启用reset_offsets=true重新消费
4. 确认Kafka中有消息存在

**问题3:消息格式解析失败**

**解决方法**:
1. 检查value_deserializer设置(默认json)
2. 定义正确的message_schema
3. 使用debug_mode=true查看原始消息
4. 使用sample_data输出查看样本

| topics | String | 是 | - |
| group_id | String | 否 | langflow-etl-consumer |
| auto_offset_reset | Dropdown | 否 | latest |
| max_messages | Integer | 否 | 100 |
| continuous_poll | Boolean | 否 | false |

## 附录 B: 常见问题汇总

### 数据源连接问题

#### 问题1: 无法连接到数据库

**症状**: "Connection refused" 或 "Access denied"

**可能原因**:
1. 数据库地址或端口错误
2. 用户名密码错误
3. 数据库防火墙限制
4. 网络不通

**解决方法**:
1. 验证数据源配置(地址、端口、用户名、密码)
2. 检查数据库是否运行: `telnet host port`
3. 检查防火墙规则,允许来源IP
4. 测试网络连通性: `ping host`
5. 查看数据库日志获取详细错误

#### 问题2: Kafka连接超时

**症状**: "TimeoutException" 或 "No brokers available"

**解决方法**:
1. 验证Kafka集群地址(bootstrap.servers)
2. 检查SASL认证配置
3. 验证topic名称是否存在
4. 增加timeout_ms参数值
5. 使用connection_test输出测试连接

#### 问题3: API调用失败

**症状**: HTTP 401/403/500错误

**解决方法**:
1. 检查认证凭据(API Key/Token)
2. 验证请求头和参数格式
3. 查看API文档确认请求格式
4. 使用Postman等工具先测试API
5. 检查API速率限制

### 数据处理问题

#### 问题4: 内存溢出 (Out of Memory)

**症状**: "java.lang.OutOfMemoryError" 或系统崩溃

**可能原因**:
1. 一次性加载数据量过大
2. 未启用分页
3. 内存泄漏
4. JVM堆内存设置过小

**解决方法**:
1. 启用分页,减小page_size(如设为500-1000)
2. 使用SQL WHERE过滤数据
3. 增加批处理的chunk_size
4. 增加Flink并行度分散数据
5. 调整JVM堆内存: `-Xmx4g`
6. 使用流式处理而非批量处理

#### 问题5: 数据类型转换失败

**症状**: "ValueError: invalid literal for int()"

**可能原因**:
1. 字符串包含非数字字符
2. 日期格式不匹配
3. 空值处理不当

**解决方法**:
1. 使用数据清洗组件预处理数据
2. 配置默认值处理空值
3. 使用try-except处理转换错误
4. 检查源数据质量

#### 问题6: 字符编码错误

**症状**: 中文显示乱码或"UnicodeDecodeError"

**解决方法**:
1. CSV组件使用encoding="auto"自动检测
2. 手动指定正确编码(UTF-8/GBK/GB2312)
3. 使用文本编辑器转换文件编码
4. 检查数据库连接字符集设置

### 性能问题

#### 问题7: 处理速度慢

**症状**: 任务执行时间过长

**解决方法**:
1. **数据库查询优化**:
   - 添加索引
   - 优化SQL查询(避免SELECT *)
   - 使用分页而非全量读取

2. **批量处理优化**:
   - 增大batch_size(5000-10000)
   - 减少字段映射复杂度
   - 使用批量插入而非单条插入

3. **并行度优化**:
   - 增加Flink并行度
   - 使用多线程处理
   - 分片处理大数据集

4. **网络优化**:
   - 减少网络传输数据量
   - 使用本地缓存
   - 压缩传输数据

#### 问题8: Flink作业运行慢

**解决方法**:
1. 增加并行度(parallelism=4或更高)
2. 调整checkpoint间隔
3. 优化算子链(operator chaining)
4. 增加TaskManager内存
5. 使用RocksDB状态后端

### 数据一致性问题

#### 问题9: 数据重复

**可能原因**:
1. 未启用去重
2. Kafka重复消费
3. 事务未提交

**解决方法**:
1. 使用去重组件
2. 设置Kafka唯一消费者组
3. 使用upsert写入模式
4. 检查事务隔离级别

#### 问题10: 数据丢失

**可能原因**:
1. 错误处理策略为skip
2. 过滤条件过严
3. 网络中断
4. 事务回滚

**解决方法**:
1. 检查错误日志
2. 调整过滤条件
3. 启用断点续传
4. 使用事务保证
5. 记录处理日志

### 数据源管理

#### 1. 数据源命名规范

**推荐命名格式**: `类型-环境-用途`

```
MySQL-生产-业务库

Flink-生产-实时计算
```

**优点**:
- 一目了然区分环境
- 避免误操作生产数据
- 便于权限管理

#### 2. 数据源连接池

**配置建议**:
```json
{
  "max_connections": 10,
  "min_connections": 2,
  "connection_timeout": 30000,
  "idle_timeout": 600000
}
```

#### 3. 数据源隔离

- 运行环境使用独立数据源
- 运行环境与运行环境分离
- 敏感数据使用专用数据源
- 定期审计数据源访问权限

### 组件配置

#### 1. 字段映射最佳实践

**明确命名**:
```json
{
  "field_mappings": [
    {"source_field": "customer_id", "target_field": "cust_id"},
    {"source_field": "order_date", "target_field": "created_at"}
  ]
}
```

#### 2. 批量大小选择

| 数据量 | 推荐batch_size | 说明 |
|--------|---------------|------|
| < 1万 | 1000 | 默认值,适合小数据 |
| 1-10万 | 5000 | 平衡内存和性能 |
| 10-100万 | 10000 | 大批量提升性能 |
| > 100万 | 分批处理 | 避免内存溢出 |

#### 3. 错误处理策略

**推荐配置**:
```json
{
  "error_handling": "log_and_skip",
  "max_errors": 100,
  "error_log_path": "/logs/etl_errors.log"
}
```

**策略选择**:
- **运行环境**: stop_on_error (便于调试)
- **运行环境**: log_and_skip (收集错误)
- **运行环境**: log_and_continue (保证可用性)
